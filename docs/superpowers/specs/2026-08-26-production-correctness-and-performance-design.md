# MONOPOMO 生产正确性与性能修复设计

## 目标

修复当前项目中已发现的缓存并发、账号隔离、扭蛋与奖励安全、统计口径、页面请求过多、历史数据查询过重和测试缺失问题，使项目具备更稳定的生产运行基础。

## 范围

本次覆盖以下模块：

1. 前端缓存与认证状态。
2. 扭蛋抽取、SSR 保底、SSR 目标和代币奖励。
3. 连续打卡、工作台和扭蛋机统计 RPC。
4. Dashboard、Gacha、DailyPlans、Reviews、Settings、PomodoroHistory、Tasks、Projects、Showcase 的查询性能。
5. 时区和逻辑日统一。
6. 数据库索引、RLS 和自动化测试基础。

不包含：产品视觉重做、全新业务功能、Cloudflare 配置修改、Supabase 线上操作、GitHub 推送。

## 设计原则

- 当前用户身份以 `auth.uid()` 为最终来源。
- 客户端不能直接伪造代币、抽卡记录或其他奖励结果。
- 逻辑日统一使用 `Asia/Shanghai`，凌晨 4 点切换。
- 首屏核心数据优先，历史和次要数据后台加载。
- 相同数据的进行中请求只执行一次。
- 所有历史列表必须有分页、时间范围或数量限制。
- 修改后先做局部测试，再做完整生产构建。

## 方案设计

### 1. 用户隔离的进行中请求缓存

在 `frontend/src/services/api.ts` 的缓存层增加进行中 Promise Map。缓存流程：

1. 当前用户不存在时返回未登录默认值。
2. 使用包含用户 ID 的缓存 key。
3. 先读取已完成且未过期的数据缓存。
4. 再读取同 key 的进行中 Promise。
5. 没有缓存时发起请求并保存 Promise。
6. 成功后写入数据缓存。
7. 无论成功或失败都清理进行中 Promise。

登出和用户切换时清空用户相关缓存，避免账号之间串数据。

### 2. 扭蛋和代币服务端安全

扭蛋 RPC 不再信任前端传入的用户 ID、日期和月份。服务端自行获取当前用户和逻辑日期，并校验抽取次数只能为 1 或 10。

代币奖励改为受控服务端函数。客户端只能请求“某个合法行为是否可以奖励”，不能直接写入任意金额和来源。奖励函数负责：

- 校验当前用户。
- 校验行为来源和固定金额。
- 校验每日去重。
- 在必要时使用唯一约束或事务避免并发重复奖励。

RLS 继续允许用户读取自己的流水，但限制客户端直接插入奖励流水；服务端函数使用最小权限并固定 `search_path`。

### 3. 统计与时区统一

连续打卡、工作台和扭蛋机统计都使用同一逻辑日计算。RPC 返回明确的 JSON 结构，前端类型与字段保持一致。

连续打卡读取有效活动日期集合，从当前逻辑日向前直到第一个空缺，不设置 365 天硬上限。对于长期大数据量，使用组合索引；后续可升级为每日活动汇总表。

### 4. 页面性能

Dashboard：核心数据和次要数据分离，避免项目数量、历史会话阻塞首屏。

Gacha：首屏只读取物品、余额和抽取核心状态；历史、任务和流水后台加载。

其他页面：

- 历史列表分页或限制最近记录。
- Reviews 避免重复加载同一筛选结果。
- Settings 使用批量评论统计或展开加载。
- DailyPlans 按月份查询。
- PomodoroHistory 使用分页明细和聚合统计。
- Tasks、Projects 在服务端完成筛选和排序。
- Showcase 读取汇总数据而不是全量历史。

### 5. 数据库索引

根据实际查询增加用户、来源、时间和状态组合索引，并通过查询计划验证索引有效性。优先覆盖：

- `token_records(user_id, source, created_at)`
- `gacha_records(user_id, created_at)`
- `pomodoro_sessions(user_id, type, status, start_time)`
- `reviews(user_id, date)`
- `daily_plans(user_id, date)`
- `tasks(user_id, status, created_at)`

### 6. 测试

优先增加纯函数和服务边界测试，覆盖：

- 进行中请求合并。
- 请求失败后重新请求。
- 用户缓存隔离。
- 逻辑日跨凌晨 4 点。
- 连续打卡断档和长期连续。
- 扭蛋抽取次数、余额、保底和目标锁定。
- 奖励每日去重和并发保护。

## 实施顺序

1. 缓存层和用户隔离。
2. 统计 RPC 与时区统一。
3. 扭蛋 RPC 安全与奖励写入边界。
4. Dashboard、Gacha 及其他页面性能修复。
5. 索引和查询验证。
6. 测试、构建和本地回归。

## 验收标准

- 同一个数据 key 的并发调用只产生一次请求。
- 不同账号不能读取彼此的缓存或数据库数据。
- 客户端不能凭空制造代币奖励。
- 抽卡只能代表当前用户，且只能抽 1 次或 10 次。
- 今日、本周、本月统计在前后端口径一致。
- Dashboard 和 Gacha 的核心内容不被历史数据阻塞。
- 历史列表不存在无上限首屏查询。
- `npm run build` 成功。
- 关键测试通过。
